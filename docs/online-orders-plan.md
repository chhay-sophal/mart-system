# Online orders plan (storefront build step 4)

Detailed plan for build step 4 of [storefront-plan.md](storefront-plan.md): a shopper checks out the storefront cart, pays by KHQR or chooses to pay at the counter, and the order waits at the branch for pickup. Step 5 (the IMS "Online orders" page) builds on the staff endpoints listed here.

## The flow

```
                    ┌──────────── KHQR ────────────┐
 cart → checkout → AWAITING_PAYMENT ──paid──▶ CONFIRMED ──▶ READY ──▶ COLLECTED
                    │    │                        ▲            │
                    │    └─QR expired──▶ EXPIRED  │            │
                    │                             │            │
                    └──── pay at counter ─────────┘            │
                                                               │
          CONFIRMED / READY ──staff cancels, or (pay at counter only)
                              not collected in time──▶ CANCELLED
```

- **KHQR**: the order is created as `AWAITING_PAYMENT` with a QR code. When Bakong reports it paid, it becomes `CONFIRMED`. If the QR expires first, the order becomes `EXPIRED` and its stock is released; the cart is kept so the shopper can try again.
- **Pay at the counter**: the order is `CONFIRMED` straight away, unpaid. Staff take payment on collection.
- **Staff** (step 5) move `CONFIRMED → READY` when the bag is packed, and `READY → COLLECTED` when it's handed over (recording the payment method for pay-at-counter orders). They can cancel a confirmed order.
- **Auto-cancel**: an unpaid pay-at-counter order that isn't collected by its pickup time plus the branch's hold window is cancelled and its stock released. Paid KHQR orders are never auto-cancelled; staff resolve them (and any refund) by hand.

## Data model

New `OnlineOrder` and `OnlineOrderItem` tables, deliberately separate from `Order` (which models a till sale and requires a `terminalId`):

| Field | Notes |
|---|---|
| `id`, `storeId` | |
| `publicToken` | 128-bit random, URL-safe. The shopper's only handle on the order (`/orders/:token`). Never sequential, never the id. |
| `clientOrderUuid` | Unique. Generated by the browser per checkout attempt, so a double-submit returns the same order instead of making two. |
| `pickupCode` | 6 characters from an unambiguous alphabet (no 0/O, 1/I/L). Unique among the store's open orders. What the shopper says at the counter. |
| `status` | `AWAITING_PAYMENT`, `CONFIRMED`, `READY`, `COLLECTED`, `CANCELLED`, `EXPIRED` |
| `paymentMethod` | `KHQR` or `PAY_AT_COUNTER`; on collection of a pay-at-counter order, what was actually taken (`CASH` / `KHQR` / `CARD`) is recorded in `collectedPaymentMethod`. |
| `customerName`, `customerPhone`, `note` | Guest checkout. Phone normalised like `toBakongMobile` does. |
| `pickupAt` | Null = "as soon as it's ready". Otherwise a slot inside the branch's opening hours. |
| `holdUntil` | Pay-at-counter only: when auto-cancel kicks in. |
| `totalAmountMinor`, `currency` | Always USD, like `Order` (KHR-priced items converted at the store's `exchange_rate` setting, as POS and reports already do). |
| `cancelReason` | `STAFF`, `UNCOLLECTED`, `PAYMENT_EXPIRED` |
| `orderId` | Set on collection — see "Reports" below. |
| timestamps | `createdAt`, `paidAt`, `readyAt`, `collectedAt`, `cancelledAt` |

`OnlineOrderItem`: `productId`, `quantity`, `priceAtOrderMinor`, `currency`, plus `nameAtOrder` so the order still reads correctly if the product is renamed or deleted later.

Other schema changes:
- `PaymentTransaction.orderId` becomes optional, and gains an optional `onlineOrderId`. The KHQR code is recorded as `PENDING` when created and flipped to `PAID` / `EXPIRED`.
- `StockMovementReason` gains `ONLINE_ORDER` (stock taken) and `ONLINE_ORDER_RELEASED` (given back), with `refType: "OnlineOrder"`, `refId` set.
- `Order.terminalId` becomes optional, and `Order` gains `channel` (`POS` default, or `ONLINE`) and nothing else. Existing POS sync is untouched.

## Stock

- **Reserved when the order is placed**, in the same transaction that creates it: each line checks `stock >= quantity` and decrements, with an `ONLINE_ORDER` movement. If any line is short, the whole order is rejected with which items and how many are left, so the cart can show it. This is stricter than the till (which accepts negative stock, since the goods already left the shop) because an online order hasn't happened yet.
- **Released** (incremented back, `ONLINE_ORDER_RELEASED`) on `EXPIRED` and `CANCELLED`.
- **Not touched again** on collection.
- The POS already overwrites its local stock with the backend's on every pull, so reserved stock disappears from the tills automatically. There's still a window where a till sells the last unit offline before it syncs; that ends up as negative stock, which reconciliation already treats as a reportable state rather than an error.

## Payment (KHQR)

- Reuses `generateKhqr()` and `checkKhqrStatus()`, using the branch's own Bakong settings. Amount in the store's `main_currency` (USD by default), matching POS.
- QR lifetime stays at the existing **5 minutes**; the order's stock is held for the same time.
- The browser polls `GET /api/public/orders/:token` every 3 seconds while `AWAITING_PAYMENT`. The server only asks Bakong if it hasn't asked for this order in the last 3 seconds (so many open tabs don't multiply calls), and caches a `PAID` answer. Bakong is never called from the browser.
- If a branch has no Bakong account set up, KHQR isn't offered at that branch (a new `khqrAvailable` flag on `PublicStore`); pay at the counter still works.

## Expiry and auto-cancel

- Evaluated **lazily** whenever an order is read (status poll, staff list), and by a **sweep every minute** inside the backend process. Both call the same idempotent function, so they can't double-release stock.
- Render's free tier sleeps when idle, so the sweep can be late; lazy evaluation keeps what shoppers and staff see correct regardless, and the first sweep after waking catches up.
- Hold window: a per-store setting `online_order_hold_minutes` (default 60), counted from `pickupAt`, or from order time for "as soon as ready".

## Pickup times

- "As soon as it's ready", or a 30-minute slot today or tomorrow, within the branch's opening hours and at least 30 minutes from now.
- Validated server-side against `openingHours` in the store's timezone (the storefront's `hours.js` logic ported to the backend). Branches without listed hours only offer "as soon as it's ready".
- Ordering while a branch is closed is allowed; "as soon as ready" then means "when it opens", and the checkout says so.

## Reports

Sales reports read `Order` only. When an online order is **collected**, a matching `Order` row is created (`channel: ONLINE`, no terminal, items copied from the online order, payment method = KHQR or whatever was taken at the counter) in the same transaction, without touching stock again. So an online sale lands in the daily summary on the day it's handed over, alongside till sales, with no changes to the reports code. Its `clientOrderUuid` is the online order's, so it can never be created twice.

## API

Public (no login, under the existing per-IP limit):

| Route | |
|---|---|
| `POST /api/public/stores/:storeId/orders` | Place an order: `clientOrderUuid`, items `{productId, quantity}`, customer name/phone/note, `pickupAt` or null, `paymentMethod`. Returns the order view, including the KHQR string when paying by KHQR. Extra limit: 5 orders per IP per 10 minutes. |
| `GET /api/public/orders/:token` | Order status for the shopper (runs lazy expiry, and checks Bakong while awaiting payment). |
| `GET /api/public/stores/:storeId/pickup-slots` | The next available slots for the checkout's time picker. |

The public order view shows items, totals, status, pickup code, branch and pickup time, and the customer's name, but only the last 3 digits of the phone number.

Staff (for step 5; built and tested here, used by IMS there):

| Route | Role |
|---|---|
| `GET /api/stores/:storeId/online-orders?status=` | any staff role |
| `POST /api/stores/:storeId/online-orders/:id/ready` | any staff role |
| `POST /api/stores/:storeId/online-orders/:id/collect` | any staff role; body has `paymentMethod` for pay-at-counter orders |
| `POST /api/stores/:storeId/online-orders/:id/cancel` | INVENTORY or ADMIN |

Invalid transitions (e.g. collecting an expired order) return 409.

## Storefront

- **Checkout page** (`/checkout`): name, phone, optional note; pickup time; KHQR or pay at the counter. Shows the order summary. Items that became unavailable since they were added are flagged before submitting.
- **KHQR payment**: the QR rendered in the browser from the backend's `qrString` (a small QR library, lazy-loaded), amount, a countdown to expiry, "Waiting for payment…", and a "Save QR" button for paying from a banking app on the same phone.
- **Order page** (`/orders/:token`): status, pickup code in large type, branch, hours and directions. Kept in the browser's "my orders" list so the shopper can find it again.
- The cart is cleared once an order is confirmed.

## Testing

Backend tests for: placing an order (prices from the server, not the request); rejecting short stock without changing any stock; idempotent retries; KHQR paid and expired paths (Bakong mocked); lazy expiry and the sweep releasing stock exactly once; auto-cancel of pay-at-counter orders only; each staff transition and the invalid ones; collection creating exactly one `Order` that shows up in the daily summary; pickup-slot validation around opening hours and midnight; the public view never exposing the full phone number. Then an end-to-end run in the browser, as in steps 2 and 3.

11. Docs.

## Not in this step

SMS or push notifications (the order page is the only status channel), customer accounts, delivery, refunds inside the system, editing an order after it's placed, and showing online orders on the POS.
